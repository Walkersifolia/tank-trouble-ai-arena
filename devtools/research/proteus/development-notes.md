# PROTEUS 开发证据

本文记录用于定位问题的开发批次，不包含最终未见种子评价。第一阶段使用 6100–6102；第二阶段继续使用已暴露的 920100–920109、930100–930103 及自然多人 6100。原版对手始终不改，地图与物理来自 Web 主版；全部成绩按各自报告的道具规则解释。

## 对照来源与 Gen3 败局

导师是私有学习目录 `learning-ai/opponents/deepseek-g5-mentor.js`，头部为 `MENTOR / 导师 — DeepSeek Gen5（教师陪练版）`，原选手 ID `deepseek-g5-mentor`。它自述从 Gen3 控制器扩展瞄准候选、弹道长度、预测混合和运动搜索。第一阶段对照通过本地路径读入。随后用户明确授权导师单独公开，正式选手为 `bots/deepseek-g5-mentor.js`；这不扩大为公开 ORACLE 源码、模型或训练数据的授权，神谕训练方案与运行状态未改。

Gen3 使用公开 `bots/astra-g3-imperator.js`。seed 6100、6101 各交换出生共 4 局，Gen3 3 胜 1 负、导师 1 胜 3 负；主动击杀为 3:1，自杀、平局、对局到时及决策超时均为 0。导师 25% 只是小样本，与用户观察的约 30% 不矛盾，不能据此确认长期胜率。原始事件及死亡窗口见 `baseline-gen3-mentor.json`。

Gen3 唯一败局是 seed 6100、rotation 1：tick 110–160 持续倒车到北边界，随后改变前后行进方向；导师 tick 195 发出直射，Gen3 tick 210 后倒车退往同一射线，tick 236 被该弹直杀。记录没有持续请求移动却静止的情况，也没有脚本超时或自杀。

直接相关的模型差异：Gen3 `drive()` 先转向后平移，倒车使用前进速度，墙接触用圆形近似。正式 `TankMotion` 用本 tick 初始航向平移，区分前进/倒车速度，并使用车体与炮管碰撞形状。倒车预测因此会高估位移，贴墙转向预测也有偏差。这是吸收 Opus 运动/碰撞预测的具体理由，而非仅增加搜索候选数量。

## 多人专项与局限

Gen3 并不是只读取当前目标：它遍历所有存活敌人生成炮弹与激光威胁，但多项风险取最大值。Opus 原版在进入决斗后把所有敌人的虚拟炮线与近身风险一起乘决斗折扣，并且部分逃路只检查最近敌人。第一阶段 Gen4 v3 尝试保留所有敌人的公开威胁，并将决斗折扣限制到正在决斗的目标；该改法后来在 multifront 中再次接受独立比较，未因机制看似合理就自动纳入正式策略。

构造局使用不变 seed 6102 原地图及导师、Opus 原脚本，仅设置出生位置、第三方初始冷却和持有激光；详细设置及前三秒、死亡前窗口保存在 `scenarios-v1.json`、`scenarios-v2.json`。

| 场景 | v1 观察 | v2 观察 |
| --- | --- | --- |
| 侧方介入 | Gen3 tick 126 阵亡；Gen4 tick 488 阵亡 | Gen3 tick 105 被第三方跳弹杀；Gen4 tick 144 自弹反弹自杀 |
| 两侧交火 | Gen3 获胜并击杀 2 人；Gen4 tick 1231 阵亡 | Gen3 tick 314 阵亡；Gen4 先主动击杀导师，tick 388 被第三方直杀 |

前两类 v1 的 Gen4 最终死亡发生时已剩两人，不能把终局失败误称为忽略第三方。Gen3 同种子在两批间的结果也会变化，其搜索用真实时间截止，CPU/JIT 时序会影响实际选择，因此单场胜负不构成稳定因果结论。

激光场景提供更具体的动作证据：候选从 `(336,144)` 朝南与导师交战，西侧 `(116,144)` 的 Opus 可见地持有激光，初始冷却 0.8 秒。v1 继续朝南静瞄；v2 修复“激光命中只取全时域最大值，所有逃路都同罚”的评分后，会前后移动，但在短距离内反复改变方向，未进入掩体。附近横墙 `(192,192)→(288,192)` 可为持续向南约 80–100 px 的路径遮挡西侧射线，支持下一步只增加可持续的掩体意图。

激光是瞬时射线；移动响应不等于必然躲过跟踪瞄准。公开动作不暴露策略闭包中的目标 ID，转向符号切换也可能是正常瞄准/避弹；本研究没有把这些代理指标声称为目标切换次数或直接的视觉抽搐证据。

## v3 冻结结果

v3 在可见敌方持激光、临近可射时选择附近可达遮挡格，保持掩体目标有效性，继续让真实来弹影响机动；多人激光射段容量按实际激光敌人数分配。没有改物理或对手。

同样 seed 6100、6101 双出生的最后 12 局为：

| 对手 | v1 Gen4 胜/负/平 | v3 Gen4 胜/负/平 | v3 主动击杀 |
| --- | ---: | ---: | ---: |
| Gen3 | 3 / 1 / 0 | 3 / 1 / 0 | 3 |
| Opus | 1 / 3 / 0 | 1 / 3 / 0 | 1 |
| 导师 | 3 / 1 / 0 | 4 / 0 / 0 | 4 |

v3 共 8 次主动击杀，0 自杀、平局、故障、决策超时及对局到时；最长连续请求移动而低速为 26 tick（0.43 秒）。这个小批没有显示单挑明显退步，也不能据此宣称已稳定超越 Gen3；胜负结论交给独立未见种子评价。数据见 `development-gen4-v3.json`。

三类构造局的最后结果：侧方介入 Gen4 获胜、主动击杀 1 人（Gen3 tick 126 阵亡）；两侧交火 Gen4 tick 203 被第三方直杀（Gen3 tick 370 阵亡）；激光介入双方依然 tick 48 阵亡。Gen4 在激光局从 `(336,144)` 出发，tick 30 曾到 `(335.38,165.35)`，随后倒退，死亡时为 `(340.64,147.62)`，净位移不足 6 px，48 tick 内转向换符号 12 次。它已不再持续原地静瞄，但仍在短距离内往返，未兑现掩体意图。附近确有可利用墙影；代码中的逐 tick 局部风险/目标排序可以覆盖路径进度，可能解释掩体目标没有稳定转为撤离轨迹，但本轮未记录内部候选分数，不能断言具体哪一评分项压制了撤离。这是 v3 阶段明确存在的瓶颈，不能宣称夹击、激光或多人专项全面解决。

第一阶段上述开发共 46 局：导师/Gen3 基础 4 局、v1/v3 单挑各 12 局、v1/v2/v3 构造专项各 6 局。交付保留全部对局结果、完整选手指标、故障与必要失败短窗口；逐发事件和非关键逐步轨迹按文末规则精简。最终独立评价不使用这些开发种子。

### 公开决策模型的边界

model2 把公开源码实现的决策器作为预测器：为当前可见对手建立独立模型实例，把竞技场公开的 `state` 转换成对方视角，预测其运动与可能开火，并用随后观察到的位置误差调整预测权重。它没有读取真实对手实例、策略闭包、私有目标、随机状态或源码身份，也不以对手名字识别 Opus。仿真的模型拥有自己的记忆，预测会错；并非获得了对手实际动作。原版源码与内嵌权重的复用遵循其 MIT 来源说明，全部模型推理也计入 runner 对整个 `update()` 的正式预算。

### 接触与路线：已证实和仍属推断的部分

`development-opus-core-5-vs-opus.json` 的 seed 920101 / rotation 0 / tick 1471 败局保留 tick 1440–1470 的近身窗口。双方车心一度只有约 45–47 px，记录速度一度超过名义 153.12 px/s，最后被 Opus 近身直杀。它是接触/姿态预测失配的代表案例，不能直接写成“已证明互推导致死亡”：日志没有记录 Box2D 接触类型，而且动作对应随后一步、速度来自前一步。

源码可直接确认，正式 `TankMotion` 对多辆车联合求解 Box2D 接触，策略的 `tickTank` 主要近似墙接触。另一个独立确认的导航缺口是网格射线斜切墙端漏判，加上短路径每 tick 重算会放弃尚未完成的转角。最终导航用方向相关的车身/炮管平移扫掠和完成航点处理，解决了隔离墙角复现；保留模型与导航的整合效果仍以配对对局为准。没有修改正式物理，也没有宣称解决所有近身接触误差。

## 阶段二多人专项：正例与失败一并保留

crossfire1–5 先尝试可追踪激光风险、持续掩体路线与航点执行。短诊断证实，临时机动排序会覆盖撤离路线，跨格后过早丢弃航点会诱发切墙角；但这些版本在原始激光构造摆位仍于 tick 48–49 阵亡。修正某个中间行为不能替代存活与反击验收，也不能因为地图上有墙影就证明一定存在及时逃生路线。

crossfire6 只在 core5 外层增加多人武器急危目标选择，保留目标滞回。它确实由南方转向西侧激光敌人，但正式单场只射出开局朝南的一发，tick 50 阵亡（core5 对照 tick 48）。火控短诊断发现：已有一发在场后门槛为 0.6828，面对西侧的 0.3622、0.5535 命中估计会在射后安全检查前被拒绝。

crossfire7 尝试有增量封路依据的反压：仅在多人、仍暴露于即将可射的激光敌人、保留弹位且预测可命中时，统计新弹额外封住的原本安全机动，并继续要求自身实际已选轨迹能避开该弹。一次独立短诊断中，tick 12 新增封住 3 个机动（1 个保持炮向）才开火；只增加 0–1 个机动时拒绝。正式构造局从 1 发增加到 4 发，仍在 tick 49 被反弹激光击杀，0 主动击杀。该反压射击未改善存活，未纳入正式选手。公开弹速为 180 px/s，不能把 220 px 的飞行时间假定成 0.3 秒；这些失败也不是“局面数学上无解”的证明。

自然第三方案例见 `development-natural-ffa.json` 的 Gen3 / rotation 0：tick 120–210 的炮口大致朝向 Opus，导师 tick 152 发出的 projectile 6 在 tick 190–200 反弹，tick 240 仍公开可见，tick 249 击杀 Gen3。这里依据朝向与弹道描述行为，没有把朝向等同于不可见的内部目标 ID。相同自然出生的 core5 于 tick 208 先反弹击杀导师，最后 tick 504 与 Opus 互杀平局。该批 Gen3 为 0/3/0、0 主动击杀；core5 为 0/2/1、2 主动击杀。core5 的另外两败分别涉及近处 Opus 对决与五弹在场时的撤离，不能全部包装成忽略第三方。

最后的 multifront 基于 integrated3，只在多人增加急危目标评分、仅限当前目标的对决折扣、联合近程敌人的下一枪退路，并补全多激光射段容量。它未修改内嵌决策模型，也未合入前述特殊激光路线和反压射击。必要对照结果如下。

| 开发场景 | integrated3 | multifront |
| --- | --- | --- |
| 自然三人 seed 6100，三席轮换 | 3 胜，5 主动击杀 | 1 胜 2 负，2 主动击杀；两败均在三人存活时率先阵亡 |
| 侧方介入 | tick 62 杀导师，tick 302 被第三方反弹杀 | tick 100 被第三方直杀，0 主动击杀 |
| 两侧夹击 | tick 611 被导师杀 | tick 196、311 连杀两敌获胜 |
| 激光介入 | tick 48 阵亡 | tick 48 阵亡 |

这组自然局及构造局均无自杀、脚本故障和决策超时。multifront 有一个夹击正例，同时有明确不利样本；没有用多人总胜率替代专项，也未继续消融后把退步武断归因于单个模块，因此整套多人策略未采用。原激光构造场景依然是明确未解决的限制。
